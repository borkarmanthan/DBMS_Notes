⚠️ Why Normalize? The Three Anomalies

A poorly designed table stores the same fact in multiple places. That redundancy causes three kinds of problems every time the data changes.
AnomalyWhat HappensExample
InsertionCan't add a fact without an unrelated fact also being presentCan't add a new course until a student enrolls in it
UpdateSame fact repeated in many rows — update all or data goes inconsistentdept_name changes → must update every student row in that dept
DeletionDeleting one fact accidentally deletes anotherLast student in a dept drops out → department record disappears too
The fix: Normalization is the step-by-step process of decomposing a table so each fact is stored in exactly one place.

1️⃣ First Normal Form (1NF)

A relation is in 1NF if every attribute holds a single, atomic value — no repeating groups, no multivalued columns.

❌ Violates 1NF

roll_nonamephone
101Rahul9900011, 9900022

✅ Fixed — 1NF

roll_nonamephone
101Rahul9900011
101Rahul9900022
Multivalued attributes get their own table entirely: student_phone(roll_no, phone) — never store them as a comma-separated string.

2️⃣ Second Normal Form (2NF)

1NF + no partial dependency: every non-key attribute must depend on the whole composite primary key, not just part of it. (Only relevant when the PK has more than one column.)

Example — Violates 2NF

enrollment(roll_no, course_id, course_name, grade) PK = (roll_no, course_id) FD: (roll_no, course_id) → grade ✅ full dependency FD: course_id → course_name ❌ PARTIAL — only needs course_id
Fix — decompose:
enrollment(roll_no, course_id, grade)
course(course_id, course_name)

3️⃣ Third Normal Form (3NF)

2NF + no transitive dependency: a non-key attribute must not depend on another non-key attribute.

Example — Violates 3NF

student(roll_no, name, dept_id, dept_name) PK = roll_no FD: roll_no → dept_id ✅ direct FD: dept_id → dept_name ❌ TRANSITIVE (non-key → non-key) FD: roll_no → dept_name (only holds because of the chain above)
Fix — decompose:
student(roll_no, name, dept_id)
department(dept_id, dept_name)

🔒 Boyce-Codd Normal Form (BCNF)

For every FD X → Y in the relation, X must be a super key. No exceptions — this is stricter than 3NF.

The One Question to Ask

For every FD X → Y:

"Is X a super key?" → YES: fine. → NO: violates BCNF.

3NFBCNF
RuleNo transitive dependency (with a prime-attribute exception)Every determinant must be a super key — no exceptions
StrictnessLooserStricter
GuaranteeAlways dependency-preservingAlways lossless, NOT always dependency-preserving
Every relation in BCNF is also in 3NF — but not every 3NF relation is in BCNF. This gap is a favorite exam question.

🔧 Hands-On: Normalize to BCNF

StudentCourseFaculty — one flat table, four violations

StudentCourseFaculty(roll_no, course_id, course_name, faculty_id, faculty_name, dept_id, dept_name, grade) FDs: (roll_no, course_id) → grade course_id → course_name, faculty_id faculty_id → faculty_name, dept_id dept_id → dept_name
Final BCNF schema (same as Session 2 College DB!):
department(dept_id, dept_name)
faculty(faculty_id, faculty_name, dept_id)
course(course_id, course_name, faculty_id)
enrollment(roll_no, course_id, grade)
