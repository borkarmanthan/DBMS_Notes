🔄 What is a Transaction?

A transaction is a sequence of one or more operations treated as a single logical unit of work — it either completes entirely, or has no effect at all.

Transaction State Diagram

Active → Partially Committed → Committed ↓ Failed → Aborted
  • Active: operations are being executed
  • Partially Committed: last operation done, not yet made durable
  • Committed: changes are permanent
  • Failed / Aborted: something went wrong, all changes rolled back

🧪 ACID Properties

PropertyGuaranteeExample
AtomicityAll operations succeed, or none doBank transfer: debit + credit both happen, or neither does
ConsistencyDB moves from one valid state to anotherTotal money in the bank stays the same after a transfer
IsolationConcurrent transactions don't see each other's uncommitted stateYou never see a half-finished transfer from another user
DurabilityCommitted changes survive even a crashPower failure right after COMMIT doesn't lose the transfer

⚠️ Four Concurrency Problems

ProblemWhat Happens
Dirty ReadReading another transaction's UNCOMMITTED data
Lost UpdateTwo transactions overwrite each other's write
Unrepeatable ReadSame query, different result, within one transaction
Phantom ReadA re-run query returns brand new rows that appeared
These four problems only happen because transactions run concurrently. Concurrency control exists specifically to prevent them — with a cost in performance.

🔒 Locking & Two-Phase Locking

Shared (S) Lock

For reading. Multiple transactions can hold an S lock on the same item together.

Exclusive (X) Lock

For writing. Only ONE transaction can hold an X lock — blocks all others.

Two-Phase Locking (2PL)

Growing Phase Shrinking Phase (acquire locks only) → (release locks only)
2PL guarantees serializability — but it does NOT guarantee freedom from deadlocks. That distinction is a very common exam trap.

🎚️ Isolation Levels

LevelDirty ReadUnrepeatable ReadPhantom Read
Read Uncommitted❌ Allowed❌ Allowed❌ Allowed
Read Committed✅ Prevented❌ Allowed❌ Allowed
Repeatable Read✅ Prevented✅ Prevented❌ Allowed
Serializable✅ Prevented✅ Prevented✅ Prevented
Stricter isolation = safer data, but more locking and blocking = slower throughput. Choosing an isolation level is a trade-off, not a default to leave untouched.

💀 Deadlocks & Hands-On

A deadlock happens when Transaction A holds a lock Transaction B needs, and Transaction B holds a lock Transaction A needs — both wait forever.

Hands-On: Two MySQL Sessions

-- Session A START TRANSACTION; UPDATE student SET cgpa = 9.5 WHERE roll_no = 101; -- do NOT commit yet -- Session B (default Read Committed) SELECT cgpa FROM student WHERE roll_no = 101; -- returns the OLD value: dirty read prevented by default -- Only after Session A commits does Session B see 9.5
