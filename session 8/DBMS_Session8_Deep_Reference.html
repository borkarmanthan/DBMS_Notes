1. What is a Transaction? Transaction States

A transaction is a sequence of one or more operations treated as a single logical unit of work — it either completes entirely, or has no effect at all.
Active → Partially Committed → Committed ↓ Failed → Aborted
  • Active — operations are currently executing
  • Partially Committed — last operation finished, but not yet made durable
  • Committed — changes are permanent and visible to others
  • Failed / Aborted — something went wrong; everything rolls back, as if it never happened
Teaching hook: "What happens if the power goes out right between the debit and the credit?" That gap is exactly what Partially Committed vs Committed distinguishes — the state where work is done but not yet guaranteed to survive a crash.

2. ACID Properties — Worked Example

Use one running example — transferring ₹500 from Account A to Account B — for all four properties. Don't switch examples per letter.

PropertyGuaranteeIn the Transfer
AtomicityAll operations succeed, or none doDebit A and credit B both happen, or neither does
ConsistencyDB moves from one valid state to another valid stateTotal money across both accounts is identical before and after
IsolationConcurrent transactions don't see each other's uncommitted stateNo one else ever sees money "missing" from A but not yet "arrived" in B
DurabilityCommitted changes survive even a crashPower failure right after COMMIT does not lose the transfer
Common mix-up: Consistency vs Isolation. Consistency asks "is the final state valid?" Isolation asks "can anyone peek at my in-progress work?" They sound similar but answer completely different questions.

3. Four Concurrency Problems — Mini Scenarios

These problems exist only because multiple transactions run against the same data at the same time.

Dirty Read

Transaction B reads a value Transaction A wrote but hasn't committed yet.

A: UPDATE student SET cgpa=9.5 WHERE roll_no=101; -- not committed B: SELECT cgpa FROM student WHERE roll_no=101; -- reads 9.5 A: ROLLBACK; -- cgpa reverts to 8.0 -- B acted on a value that never actually existed

Lost Update

Two transactions read the same value, compute independently, and one write silently overwrites the other.

A reads cgpa = 8.0, computes 8.0 + 0.5 = 8.5, writes 8.5 B reads cgpa = 8.0, computes 8.0 + 0.3 = 8.3, writes 8.3 (overwrites A) -- A's +0.5 update is lost entirely

Unrepeatable Read

Same transaction reads the same row twice, gets two different values.

-- Within ONE transaction: SELECT cgpa FROM student WHERE roll_no=101; -- 8.0 ...(another transaction commits an update here)... SELECT cgpa FROM student WHERE roll_no=101; -- 8.5 (changed!)

Phantom Read

Same range query re-run, and a brand-new row appears.

SELECT * FROM student WHERE dept_id=1; -- returns 10 rows ...(another transaction inserts+commits an 11th student in dept 1)... SELECT * FROM student WHERE dept_id=1; -- returns 11 rows
Quick test for students: Unrepeatable Read = same row, different value. Phantom Read = same query, different row count.

4. Locking & Two-Phase Locking

LockPurposeRule
Shared (S)ReadingMultiple transactions can hold it on the same item together
Exclusive (X)WritingOnly ONE transaction can hold it — blocks all others

Two-Phase Locking (2PL)

Growing Phase Shrinking Phase (acquire locks only) → (release locks only)

Once a transaction releases its first lock, it may never acquire a new one. This strict separation is what guarantees serializability.

The exam trap — say this verbatim in class:
"2PL guarantees serializability. It does NOT guarantee freedom from deadlocks."
A transaction can follow 2PL perfectly and still wait forever on a lock someone else holds. These are two separate guarantees.

5. Isolation Levels

LevelDirty ReadUnrepeatable ReadPhantom Read
Read Uncommitted❌ Allowed❌ Allowed❌ Allowed
Read Committed✅ Prevented❌ Allowed❌ Allowed
Repeatable Read✅ Prevented✅ Prevented❌ Allowed
Serializable✅ Prevented✅ Prevented✅ Prevented
Trap to flag: "Read Committed" sounds safe, but it does not prevent Unrepeatable Reads. The name implies more safety than it actually delivers.
Stricter isolation = safer data, but more locking/blocking = slower throughput. Choosing an isolation level is a deliberate trade-off, not a default to leave untouched.

6. Deadlocks — Worked Scenario

A deadlock happens when Transaction A holds a lock Transaction B needs, and Transaction B holds a lock Transaction A needs — both wait forever.
Transaction A: locks student row 101 → then wants to lock enrollment row for 101 Transaction B: locks enrollment row for 101 → then wants to lock student row 101 -- A waits on B's lock. B waits on A's lock. Neither can proceed. Deadlock.

Handling methods: timeout (give up after N seconds), wait-die/wound-wait schemes (based on transaction age/priority), or active deadlock detection followed by rolling back one transaction.

7. Hands-On Practicals (MySQL)

Practical 1 — Observe a Dirty Read is Prevented by Default

-- Session A START TRANSACTION; UPDATE student SET cgpa = 9.5 WHERE roll_no = 101; -- do NOT commit yet -- Session B (default isolation = Read Committed in MySQL) SELECT cgpa FROM student WHERE roll_no = 101; -- returns OLD value — dirty read prevented by default -- Only AFTER Session A commits: -- Session B SELECT cgpa FROM student WHERE roll_no = 101; -- now returns 9.5

Practical 2 — Force a Dirty Read to Happen

-- Session B, BEFORE the SELECT: SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; SELECT cgpa FROM student WHERE roll_no = 101; -- now DOES return 9.5, even though Session A hasn't committed

Practical 3 — Simulate a Lost Update

-- Session A START TRANSACTION; SELECT cgpa FROM student WHERE roll_no = 101; -- reads 8.0 UPDATE student SET cgpa = 8.5 WHERE roll_no = 101; COMMIT; -- Session B (started before A committed, using its own stale read of 8.0) START TRANSACTION; SELECT cgpa FROM student WHERE roll_no = 101; -- also reads 8.0 UPDATE student SET cgpa = 8.3 WHERE roll_no = 101; COMMIT; -- Final value is 8.3 — A's update to 8.5 is lost

Practical 4 — Build a Deadlock on Purpose

-- Session A START TRANSACTION; UPDATE student SET cgpa = 9.0 WHERE roll_no = 101; -- locks student row 101 -- (pause here) UPDATE enrollment SET grade = 'A' WHERE roll_no = 101; -- wants enrollment lock -- Session B (run while Session A is paused) START TRANSACTION; UPDATE enrollment SET grade = 'B' WHERE roll_no = 101; -- locks enrollment row 101 -- (pause here) UPDATE student SET cgpa = 8.0 WHERE roll_no = 101; -- wants student lock -- Result: MySQL detects the deadlock and automatically rolls back one transaction

Practical 5 — Compare All Four Isolation Levels

Repeat Practical 1's read using each level, and have students record the observed behavior in a table:

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; SET TRANSACTION ISOLATION LEVEL READ COMMITTED; SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

8. Full Exam Question Bank

  1. Define ACID, with one concrete example for each property.
  2. Draw and explain the transaction state diagram.
  3. Explain all four concurrency problems with an example of each.
  4. Differentiate the four isolation levels and what each one prevents.
  5. What is Two-Phase Locking, and what does it guarantee?
  6. Explain why 2PL guarantees serializability but NOT deadlock-freedom.
  7. Define deadlock and describe two ways a database can handle it.
  8. Differentiate Consistency (ACID) from Isolation (ACID) — a commonly confused pair.
  9. Why might a system deliberately choose Read Committed over Serializable?
    Model answer: performance — stricter isolation means more locking/blocking and lower throughput; Read Committed is a deliberate trade-off when the application can tolerate unrepeatable/phantom reads.
  10. Scenario: Transaction X reads a row, another transaction commits a change to it, X reads it again in the same transaction and gets a different value. Name the anomaly. (Unrepeatable Read)
  11. True/False with justification: "Read Committed prevents unrepeatable reads." (False — it only prevents dirty reads.)

9. LeetCode / Coding Connections

Being direct about this: LeetCode has no "implement 2PL" or "design isolation levels" problem — that's a systems/DBMS topic. However, LeetCode's Concurrency category (multithreading problems) is built on the exact same primitives — locks, mutual exclusion, ordering guarantees — that this session covers conceptually. These make excellent optional enrichment, especially for students comfortable with Java/Python threading.
LeetCode 1114 — Print in Order
Three threads must print "first", "second", "third" strictly in order. Direct hands-on parallel to why ordering guarantees (like 2PL's growing/shrinking discipline) matter when multiple executions interleave.
LeetCode 1115 — Print FooBar Alternately
Two threads must alternate strictly. Mirrors how a Shared vs Exclusive lock forces mutual exclusion between competing transactions.
LeetCode 1116 — Print Zero Even Odd
Three threads coordinating via semaphores — a concrete, code-level illustration of the coordination that lock managers do at the database engine level.
LeetCode 1226 — The Dining Philosophers
This is the closest LeetCode gets to teaching deadlock directly — philosophers (transactions) competing for forks (locks) in a way that can deadlock if not handled carefully. Excellent to assign right after the Deadlock section.
LeetCode 1195 — Fizz Buzz Multithreaded
Four threads must coordinate strict turn-taking — good practice for the discipline 2PL enforces (acquire only during growing phase, release only during shrinking phase).
