🎯 CORE CONCEPTS TO EMPHASIZE
═══════════════════════════════════════════════════════

  1. WHY NoSQL EXISTS
     Horizontal scaling needs (add more machines, not a bigger one)
     Flexible / schema-less data (structure varies row to row)
     High write throughput at massive scale
     Handling semi-structured or unstructured data naturally

  2. FOUR MAIN TYPES OF NoSQL DATABASES
     Key-Value (Redis, DynamoDB): simplest, O(1) lookup by key
     Document (MongoDB, CouchDB): JSON-like documents, flexible fields
     Column-family (Cassandra, HBase): optimized for write-heavy,
       wide-column workloads
     Graph (Neo4j): nodes + edges — best for relationship-heavy data

  3. CAP THEOREM
     In a distributed system, during a network partition you can
     only guarantee 2 of these 3 at once:
       Consistency: every read gets the latest write
       Availability: every request gets a response (may be stale)
       Partition Tolerance: system keeps working despite network splits
     Most real distributed NoSQL systems choose AP (available +
     partition-tolerant, eventual consistency) over strict consistency.

  4. ACID vs BASE
     ACID (traditional RDBMS): strict correctness, guaranteed consistency
     BASE (typical NoSQL): Basically Available, Soft state,
       Eventual consistency — trades strict correctness for scale/speed

  5. WHEN TO USE WHICH (the actual decision, not dogma)
     RDBMS: strong consistency, complex relationships, transactions
       (banking, the College DB itself)
     NoSQL: massive scale, flexible/evolving schema, unstructured data
       (social feeds, IoT sensor streams, product catalogs)

═══════════════════════════════════════════════════════
🔧 HANDS-ON: MODEL COLLEGE DB AS A DOCUMENT
═══════════════════════════════════════════════════════

  Relational (4 normalized tables) → one embedded JSON document:

  {
    "roll_no": 101,
    "name": "Nilisha",
    "dept": { "dept_id": 1, "dept_name": "Computer Science" },
    "enrollments": [
      { "course_id": 501, "course_name": "DBMS", "grade": "A" },
      { "course_id": 502, "course_name": "Circuits", "grade": "B" }
    ]
  }

  Discuss the trade-off explicitly:
    Benefit: one single read fetches everything about a student,
             no JOIN needed
    Cost: dept_name is now duplicated across every student document
          in that department — this is EXACTLY the update anomaly
          normalization (Session 6) was designed to eliminate.
          Document databases accept it deliberately for read speed.

  This is the full-circle moment of the entire course: normalize
  for correctness (Session 6), then knowingly denormalize for scale
  when the use case calls for it (this session).

═══════════════════════════════════════════════════════
📋 QUICK QUIZ ANSWERS
═══════════════════════════════════════════════════════

  Q1: During a network partition, CAP says you can guarantee?
      → Only 2 of the 3 (Consistency, Availability, Partition Tolerance)
  Q2: Best NoSQL type for social-network friend relationships?
      → Graph database
  Q3: What does BASE stand for?
      → Basically Available, Soft state, Eventual consistency
  Q4: Why do document databases favor embedding over referencing?
      → To avoid joins and enable fast single-document reads
  Q5: Is a document database immune to update anomalies?
      → No — embedding reintroduces the same redundancy
        normalization was designed to remove

═══════════════════════════════════════════════════════
⚠️ COMMON STUDENT MISTAKES TO WATCH FOR
═══════════════════════════════════════════════════════

  1. Thinking NoSQL means "no schema at all" (it means flexible
     schema, not zero structure)
  2. Believing NoSQL is strictly "better" or "newer/superior" to SQL
     rather than a different trade-off for a different use case
  3. Misapplying CAP — thinking you can have all 3 with clever
     engineering (you cannot, during an actual partition)
  4. Forgetting that embedding duplicates data on purpose
  5. Assuming every NoSQL database works the same way (key-value,
     document, column-family, and graph are genuinely different)

     NoSQL expertise — the goal is informed vocabulary, not mastery
  4. Close the course by mapping all 12 sessions back to the original
     5-part roadmap: theory → SQL → transactions → indexing → advanced
