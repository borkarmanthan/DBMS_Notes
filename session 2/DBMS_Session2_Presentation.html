🔑 Why Do We Need Keys?

Definition: Keys are attributes (or sets of attributes) that uniquely identify tuples (rows) in a relation. They are the foundation of database integrity.

Real-World Analogy

🏫 College Scenario: ┌─────────────────────────────────────┐ │ Roll No: 101 → Rahul Verma │ │ Roll No: 102 → Priya Sharma │ │ Roll No: 103 → Amit Patel │ └─────────────────────────────────────┘ Roll Number = KEY → Uniquely identifies YOU among 1000s of students

Without Keys = Chaos

❌ Two students with same roll_no
❌ Cannot tell who got which marks
❌ Cannot link enrollment to student
❌ Data becomes unreliable
✅ With Primary Key:
Every row has a unique identity
Relationships work perfectly
Data integrity is maintained

🏗️ Key Hierarchy

┌─────────────────────────────────────────────────────────────┐ │ ALL POSSIBLE COMBINATIONS │ │ (Every attribute set you can think of) │ ├─────────────────────────────────────────────────────────────┤ │ SUPER KEYS │ │ (Sets that ACTUALLY uniquely identify a row) │ │ Ex: {roll_no}, {email}, {roll_no,name}, {all_attrs} │ ├─────────────────────────────────────────────────────────────┤ │ CANDIDATE KEYS │ │ (Minimal Super Keys — NO extra attributes) │ │ Ex: {roll_no}, {email}, {aadhar} │ ├──────────────────────────┬──────────────────────────────────┤ │ PRIMARY KEY │ ALTERNATE KEYS │ │ (Chosen by designer) │ (Other candidate keys) │ │ Only ONE per table │ Implemented as UNIQUE │ │ Ex: roll_no │ Ex: email, aadhar │ └──────────────────────────┴──────────────────────────────────┘
Memory Trick: Super → Candidate → Primary
"Superman is a candidate for president, but only ONE can be primary."

📊 Super Key vs Candidate Key

STUDENT(roll_no, name, email, phone, aadhar_no)

🔶 SUPER KEYS

"Can uniquely identify, but might be overkill"

  • {roll_no} ✅
  • {email} ✅
  • {aadhar_no} ✅
  • {roll_no, name} ✅ (extra attr)
  • {roll_no, email} ✅ (extra attr)
  • {all attributes} ✅ (definitely unique)

Count: Many possible super keys

🟢 CANDIDATE KEYS

"The SMALLEST possible set that still works"

  • {roll_no} ✅ (minimal)
  • {email} ✅ (minimal)
  • {aadhar_no} ✅ (minimal)
❌ {roll_no, name} — name is redundant
❌ {roll_no, email} — email is redundant
❌ {all attributes} — way too many

Count: Few, minimal sets only

⭐ Primary Key (PK)

The Candidate Key chosen by the database designer to be the main unique identifier for a relation.

5 Golden Rules of Primary Key

RuleExplanationWhy It Matters
1. UNIQUENo two rows can have same PKEnsures every row is identifiable
2. NOT NULLEvery row MUST have a PKEntity Integrity — no ghost rows
3. Only ONEEach table has exactly one PKSingle source of identity
4. STABLEShould rarely changeReferences won't break
5. SIMPLEPrefer single attributeEasier to use in joins & indexes
Example: Candidate Keys = {roll_no}, {email}, {aadhar_no}
Designer chooses: roll_no as PK
Why not email? Student might switch providers → email changes → PK changes → all references break!

🔗 Foreign Key (FK)

An attribute in one table that references the Primary Key of another table. It creates relationships between tables.
┌─────────────────────────┐ ┌─────────────────────────┐ │ DEPARTMENT │ │ STUDENT │ ├─────────────────────────┤ ├─────────────────────────┤ │ PK dept_id │◄────────┤ FK dept_id │ │ dept_name │ Links │ PK roll_no │ │ location │ │ name │ └─────────────────────────┘ │ email │ PARENT TABLE └─────────────────────────┘ CHILD TABLE

Foreign Key Rules

✅ Valid Operations:
• Insert student with dept_id = 1 (if dept 1 exists)
• Insert student with dept_id = NULL (orphan allowed)
• Update student's dept_id to existing dept
❌ Invalid Operations:
• Insert student with dept_id = 99 (doesn't exist)
• Delete department that has students (without CASCADE)
• Update dept_id to non-existent department

⚡ ON DELETE / ON UPDATE Options

What happens to child rows when parent changes?

OptionBehaviorWhen to Use
CASCADEAutomatically delete/update child rowsEnrollment records when course deleted
SET NULLSet FK to NULLStudent dept when department restructured
RESTRICTPrevent parent deletion/updatePrevent deleting department with students
NO ACTIONSame as RESTRICTDefault behavior
-- Example: If department deleted, set student's dept to NULL FOREIGN KEY (dept_id) REFERENCES department(dept_id) ON DELETE SET NULL ON UPDATE CASCADE -- Example: If course deleted, delete all enrollments too FOREIGN KEY (course_id) REFERENCES course(course_id) ON DELETE CASCADE

🧩 Composite Key

A primary key made of two or more attributes together. Used when no single column is unique enough.

Example: ENROLLMENT Table

ENROLLMENT(roll_no, course_id, grade, enrollment_date) roll_no alone? ❌ (student takes multiple courses) course_id alone? ❌ (multiple students in one course) grade alone? ❌ (many students get same grade) {roll_no, course_id}? ✅ → Student 101 + Course 1 = Unique enrollment → Student 101 + Course 2 = Different enrollment → Student 102 + Course 1 = Different enrollment
CREATE TABLE enrollment ( roll_no INT, course_id INT, grade CHAR(2), PRIMARY KEY (roll_no, course_id), -- Composite Key FOREIGN KEY (roll_no) REFERENCES student(roll_no), FOREIGN KEY (course_id) REFERENCES course(course_id) );

🛡️ Integrity Constraints

Rules that ensure accuracy, consistency, and reliability of data

🔴 Entity Integrity

Primary Key cannot be NULL

-- This FAILS: INSERT INTO student VALUES (NULL, 'Rahul', ...); ERROR: PK cannot be null!

🔵 Referential Integrity

FK must match PK or be NULL

-- This FAILS: INSERT INTO student VALUES (105, 'X', ..., 99); ERROR: dept_id 99 doesn't exist!

🟢 Domain Integrity

Values must be from specified domain

-- This FAILS: INSERT INTO student VALUES (..., 15.0, ...); ERROR: cgpa must be 0-10!

💻 SQL: Create Tables

-- Step 1: Create Database DROP DATABASE IF EXISTS college_mgmt; CREATE DATABASE college_mgmt; USE college_mgmt; -- Step 2: DEPARTMENT (Parent Table) CREATE TABLE department ( dept_id INT PRIMARY KEY, dept_name VARCHAR(50) NOT NULL UNIQUE, location VARCHAR(50) DEFAULT 'Main Building', hod_name VARCHAR(50), established_year INT CHECK (established_year >= 1950) ); -- Step 3: STUDENT (Child Table) CREATE TABLE student ( roll_no INT PRIMARY KEY, name VARCHAR(50) NOT NULL, email VARCHAR(50) UNIQUE NOT NULL, phone VARCHAR(15), dob DATE, gender CHAR(1) CHECK (gender IN ('M', 'F', 'O')), dept_id INT, admission_date DATE DEFAULT CURRENT_DATE, cgpa DECIMAL(3,2) CHECK (cgpa >= 0.00 AND cgpa <= 10.00), FOREIGN KEY (dept_id) REFERENCES department(dept_id) ON DELETE SET NULL ON UPDATE CASCADE );

💻 SQL: Enrollment & Data

-- Step 4: COURSE CREATE TABLE course ( course_id INT PRIMARY KEY, course_code VARCHAR(10) UNIQUE NOT NULL, course_name VARCHAR(100) NOT NULL, credits INT CHECK (credits BETWEEN 1 AND 6), semester INT CHECK (semester BETWEEN 1 AND 8), dept_id INT, FOREIGN KEY (dept_id) REFERENCES department(dept_id) ON DELETE CASCADE ); -- Step 5: ENROLLMENT (Composite Key!) CREATE TABLE enrollment ( roll_no INT, course_id INT, semester INT CHECK (semester BETWEEN 1 AND 8), grade CHAR(2) CHECK (grade IN ('AA', 'AB', 'BB', 'BC', 'CC', 'CD', 'DD', 'FF')), enrollment_date DATE DEFAULT CURRENT_DATE, PRIMARY KEY (roll_no, course_id, semester), FOREIGN KEY (roll_no) REFERENCES student(roll_no) ON DELETE CASCADE, FOREIGN KEY (course_id) REFERENCES course(course_id) ON DELETE CASCADE );

🎓 Quick Quiz (5 Questions)

Q1. Alternate Key

Table has unique emp_id, email, pan. emp_id is PK. What is email called?

A: Alternate Key

Q2. NULL in PK?

Can a primary key contain NULL? Why?

A: No — Entity Integrity requires PK to be NOT NULL

Q3. Composite Key

ENROLLMENT(roll_no, course_id, grade). Best PK?

A: (roll_no, course_id) — Composite Key

Q4. Delete Department

What happens if you delete a dept with students (no CASCADE)?

A: Error — Referential Integrity prevents it

Q5. Marks Constraint

What constraint ensures marks are between 0 and 100?

A: CHECK constraint (Domain Integrity)
