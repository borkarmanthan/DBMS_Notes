ER Model is the bridge between user requirements and the actual database implementation. It was proposed by Peter Chen (1976).

Why ER Model?

  • Easy for non-technical stakeholders
  • Visual representation of data
  • Independent of any DBMS
  • Foundation for relational schemas

Key Components

  • Entities — Real-world objects
  • Attributes — Properties of entities
  • Relationships — Associations between entities

📊 Types of Attributes

🔵 Simple (Atomic)

Cannot be divided further

Ex: roll_no, age, salary

🟠 Composite

Can be divided into sub-parts

Ex: name = (first, middle, last)
address = (street, city, pin)

🟢 Multivalued

Can have multiple values

Ex: phone numbers, emails
Represented by { } or double oval

🟣 Derived

Computed from other attributes

Ex: age = current_date − dob
total_marks = sum of subjects

🔗 Relationships & Cardinality

One-to-One (1:1)

One A ↔ One B

EMPLOYEE ───1─── manages ───1─── DEPARTMENT

One employee manages one dept
One dept has one manager

One-to-Many (1:N)

One A → Many B

DEPARTMENT ───1─── has ───N─── EMPLOYEE

One dept has many employees
Each employee belongs to one dept

Many-to-Many (M:N)

Many A ↔ Many B

STUDENT ───M─── enrolls ───N─── COURSE

One student enrolls in many courses
One course has many students

Participation Constraints

Total: Every entity MUST participate
(double line)

Partial: Some entities MAY participate
(single line)

🎭 Weak Entities

A Weak Entity cannot be uniquely identified by its own attributes. It depends on an Identifying Owner for its existence and identity.
EMPLOYEE ════════1════════ has ════════N════════ ╔═══════════════╗ (emp_id, name) (total) (total) ║ DEPENDENT ║ ║ (dep_name) ║ ← Partial Key ╚═══════════════╝ Double rectangle = Weak Entity Double diamond = Identifying Rel. Double line = Total Participation

Characteristics

  • Has a partial key (discriminator)
  • Needs owner's PK for full identity
  • Total participation in identifying relationship
  • Represented by double rectangle

Relational Mapping

CREATE TABLE dependent ( emp_id INT, dep_name VARCHAR(50), relationship VARCHAR(20), PRIMARY KEY (emp_id, dep_name), FOREIGN KEY (emp_id) REFERENCES employee(emp_id) );

💻 Complete Mapping Example

College System: Department, Student, Course, Faculty, Enrollment

DEPARTMENT(dept_id PK, dept_name, location) │ │ 1 has N ▼ STUDENT(roll_no PK, name, dob, gender, cgpa, dept_id FK) student_phone(roll_no FK, phone PK) │ │ M enrolls N ▼ COURSE(course_id PK, course_code, course_name, credits, dept_id FK, faculty_id FK) ▲ │ 1 teaches N │ FACULTY(faculty_id PK, first_name, last_name, salary, dept_id FK) ENROLLMENT(roll_no FK, course_id FK, semester, grade, PRIMARY KEY(roll_no, course_id, semester))
Key Takeaway: Every entity → table. Every M:N → junction table. Every multivalued → separate table.
