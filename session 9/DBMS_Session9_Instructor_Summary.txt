═══════════════════════════════════════════════════════
🎯 CORE CONCEPTS TO EMPHASIZE
═══════════════════════════════════════════════════════

  1. QUERY PROCESSING PIPELINE
     Parser (syntax/semantic check) → Query Translation (SQL to
     relational algebra) → Optimizer (pick the cheapest plan) →
     Execution Engine (runs the chosen plan)

  2. COST IS DOMINATED BY DISK I/O
     Fewer disk block reads = cheaper query, almost always —
     CPU comparison cost is usually negligible next to disk access

  3. JOIN ALGORITHMS (know when each wins)
     Nested Loop Join: simplest, fine when one side is tiny or indexed
     Block Nested Loop: reads in blocks to cut disk I/O vs row-by-row
     Sort-Merge Join: great when both inputs are already sorted
     Hash Join: builds a hash table on the smaller relation — best for
       large, unsorted equi-joins

  4. OPTIMIZATION TECHNIQUES
     Predicate Pushdown: filter rows as early as possible, before joins
     Projection Pushdown: select only needed columns early
     Join Order: put the most selective filter/smallest result first
     Never SELECT * when only specific columns are needed

  5. EXPLAIN "type" COLUMN — BEST TO WORST
     system > const > eq_ref > ref > range > index > ALL
     ALL = full table scan = the thing you're trying to avoid

  6. EXPLAIN "Extra" COLUMN RED FLAGS
     "Using filesort"   → sorting had to happen outside index order
     "Using temporary"  → MySQL built a temp table mid-query
     "Using index"      → GOOD: query satisfied by index alone

═══════════════════════════════════════════════════════
🔧 HANDS-ON: DIAGNOSE & FIX A SLOW QUERY
═══════════════════════════════════════════════════════

  Query:
    SELECT s.name, c.course_name, e.grade
    FROM enrollment e
    JOIN student s ON e.roll_no = s.roll_no
    JOIN course c ON e.course_id = c.course_id
    WHERE s.dept_id = 1
    ORDER BY e.grade;

  Step 1: EXPLAIN it — look for "Using filesort" (grade isn't indexed
          in sorted order) and check the "type"/"rows" columns.
  Step 2: Add a composite index: CREATE INDEX idx_enroll_grade
          ON enrollment(course_id, grade);
  Step 3: Re-run EXPLAIN — compare rows scanned and whether
          "Using filesort" disappears.
  Step 4: Discuss: does adding this index help or hurt other queries
          that write to enrollment frequently?

📋 QUICK QUIZ ANSWERS

  Q1: Correct order of query processing steps?
      → Parse → Translate → Optimize → Execute
  Q2: Which join algorithm builds a hash table on the smaller relation?
      → Hash Join
  Q3: What does "Using filesort" mean in EXPLAIN?
      → MySQL had to sort results outside of any index order
  Q4: Which EXPLAIN type is fastest?
      → const / system (exact single-row lookup)
  Q5: What is predicate pushdown?
      → Applying filters as early as possible to reduce rows processed

═══════════════════════════════════════════════════════
⚠️ COMMON STUDENT MISTAKES TO WATCH FOR
═══════════════════════════════════════════════════════

  1. Assuming the optimizer always picks the objectively best plan
     (it picks the cheapest ESTIMATED plan — estimates can be wrong)
  2. Confusing "Using index" (good) with "Using filesort" (bad)
  3. Adding an index and never re-checking EXPLAIN to confirm it's used
  4. Ignoring that every extra index slows down INSERT/UPDATE/DELETE
  5. Writing SELECT * out of habit even when only 2 columns are needed
  6. Assuming hash join is always best (it needs memory for the hash
     table — sort-merge can win when data is already sorted)

💡 TEACHING TIPS
═══════════════════════════════════════════════════════

  1. Run EXPLAIN on the same query before AND after every change live

     hash join = sorting books into labeled bins first

     ask them to name where their own query's type falls
