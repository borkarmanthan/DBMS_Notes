🤔 What Is a JOIN, and Why Do We Need It?

Normalization (Session 6) splits data across multiple tables to avoid redundancy. A JOIN is how you put it back together for a query.
student (roll_no, name, dept_id) + department (dept_id, dept_name) ↓ JOIN on dept_id ↓ "Nilisha is in Computer Science" — one combined row

Without a JOIN, you'd need a separate query per table and combine the results yourself in application code. A JOIN lets the database do that combination in one step, using a shared column.

🗺️ The Six Join Types — Overview

Join TypeKeeps
INNER JOINOnly rows with a match in BOTH tables
LEFT JOINALL rows from the left table, matched or not
RIGHT JOINALL rows from the right table, matched or not
FULL OUTER JOINALL rows from both tables, matched or not
SELF JOINA table joined to itself
CROSS JOINEvery row paired with every row (no condition)
Every one of these uses the same basic syntax shape — FROM table1 [JOIN TYPE] table2 ON condition. The keyword before JOIN is the only thing that changes.

🔵 INNER JOIN — The Default

Student Department ●●●●● ●●●● ╲ ╱ ╲ ●●●● ╱ ← only the OVERLAP is returned ╲__╱____╲__╱
SELECT s.name, d.dept_name FROM student s INNER JOIN department d ON s.dept_id = d.dept_id;
Writing just JOIN (without INNER) means the same thing — INNER is the default and is often omitted.

🔵 INNER JOIN — Worked Example

⬅️ LEFT JOIN — Keep Everything on the Left

Student (LEFT) Department (RIGHT) ●●●●●●●● ●●●● └───┬───┘ │ ALL of these only matches returned, even from here are with NULL on attached the right side
SELECT s.name, d.dept_name FROM student s LEFT JOIN department d ON s.dept_id = d.dept_id;
If a student's dept_id doesn't match any department, dept_name simply shows as NULL — the student row is still returned.

⬅️ LEFT JOIN — Finding "Missing" Data

LEFT JOIN's most powerful real use: finding rows in the left table that have NO match at all.

-- Students with NO enrollments SELECT s.name FROM student s LEFT JOIN enrollment e ON s.roll_no = e.roll_no WHERE e.roll_no IS NULL;
This pattern — LEFT JOIN + WHERE right_table.column IS NULL — is the standard way to find "orphaned" or unmatched records in SQL.

➡️ RIGHT JOIN — Keep Everything on the Right

Student (LEFT) Department (RIGHT) ●●●● ●●●●●●●● │ └───┬───┘ only matches ALL of these from here are returned, even attached with NULL on the left side
SELECT s.name, d.dept_name FROM student s RIGHT JOIN department d ON s.dept_id = d.dept_id;
RIGHT JOIN is just LEFT JOIN with the tables swapped — most developers standardize on always using LEFT JOIN (rewriting the FROM order) purely for consistency, since RIGHT JOIN is used far less often.

↔️ LEFT vs RIGHT — Side by Side

LEFT JOINRIGHT JOIN
Keeps unmatched rows fromThe table listed FIRST (left)The table listed SECOND (right)
Equivalent rewrite—Swap table order + use LEFT JOIN

-- These two queries return identical results: SELECT * FROM A RIGHT JOIN B ON A.id = B.id; SELECT * FROM B LEFT JOIN A ON A.id = B.id;

⬛ FULL OUTER JOIN — Keep Absolutely Everything

Student Department ●●●●●●●● ●●●●●●●● └────┬─────────────┬────┘ ALL rows from BOTH sides, matched or not
MySQL does NOT support FULL OUTER JOIN directly. It must be simulated with a UNION of a LEFT JOIN and a RIGHT JOIN.
SELECT s.name, d.dept_name FROM student s LEFT JOIN department d ON s.dept_id = d.dept_id UNION SELECT s.name, d.dept_name FROM student s RIGHT JOIN department d ON s.dept_id = d.dept_id;

🔁 SELF JOIN — A Table Joined to Itself

Needed whenever a table has a relationship to ITSELF — the classic case is an employee table where each row also stores its own manager's ID.
-- employee(emp_id, name, manager_id) SELECT e.name AS employee, m.name AS manager FROM employee e JOIN employee m ON e.manager_id = m.emp_id;

✖️ CROSS JOIN — Every Combination, No Condition

CROSS JOIN pairs EVERY row of one table with EVERY row of the other. 100 students × 20 courses = 2,000 rows — almost always more than intended.
SELECT s.name, c.course_name FROM student s CROSS JOIN course c;
Legitimate use case: generating every possible pairing on purpose — e.g. a scheduling tool listing every student/timeslot combination to then filter down from.

Accidental CROSS JOIN warning: writing a comma-separated FROM list without a WHERE condition silently produces a CROSS JOIN: FROM student, course — always prefer explicit JOIN syntax to avoid this.

🌿 NATURAL JOIN — Automatic Matching (Use With Care)

SELECT * FROM student NATURAL JOIN department; -- automatically joins on ALL identically-named columns
NATURAL JOIN guesses the join column by matching column NAMES automatically — if both tables happen to share an unrelated column with the same name, you get silently wrong results. Most real-world style guides recommend always using explicit ON conditions instead.

🔗 Joining Three or More Tables

Chain JOINs one after another — each new JOIN can reference any table already brought into the query.

SELECT s.name, d.dept_name, c.course_name, e.grade FROM student s JOIN department d ON s.dept_id = d.dept_id JOIN enrollment e ON s.roll_no = e.roll_no JOIN course c ON e.course_id = c.course_id;
Order of the JOIN clauses in the query doesn't change the result — but a sensible order (following the natural relationship chain) makes the query far easier to read and debug.

⚖️ JOIN vs Subquery — When to Use Which

JOINSubquery (Session: Nested Queries)
Best forCombining columns from multiple tables into one rowFiltering based on a condition computed separately
PerformanceUsually faster — optimizer handles it directlyCorrelated subqueries can be slower (re-run per row)
ReadabilityClear when you need columns from both tablesClearer when you only need existence/comparison, not extra columns
-- Same logical result, two approaches: SELECT DISTINCT s.name FROM student s JOIN enrollment e ON s.roll_no = e.roll_no; SELECT name FROM student WHERE roll_no IN (SELECT roll_no FROM enrollment);

⚡ Performance: Indexes & Joins

A join column with NO index forces a full scan of one table for every row of the other — this is exactly the "nested loop without an index" scenario from Session 9's join algorithms.
-- Foreign key columns used in JOINs should almost always be indexed CREATE INDEX idx_enrollment_roll ON enrollment(roll_no); CREATE INDEX idx_enrollment_course ON enrollment(course_id);

Run EXPLAIN on any multi-table join query — if you see type: ALL on a joined table, that's a strong signal the join column needs an index (Session 7/9).

📋 Quick Quiz

Q1. Which join type returns rows even when there's no match on either side?

A: FULL OUTER JOIN

Q2. How do you simulate FULL OUTER JOIN in MySQL?

A: UNION of a LEFT JOIN and a RIGHT JOIN

Q3. What pattern finds unmatched rows using a LEFT JOIN?

A: LEFT JOIN + WHERE right_table.column IS NULL

Q4. Why does a self-join require table aliases?

A: SQL can't otherwise distinguish the two "copies" of the same table

Q5. What silently causes an accidental CROSS JOIN?

A: A comma-separated FROM list with no WHERE condition linking the tables
