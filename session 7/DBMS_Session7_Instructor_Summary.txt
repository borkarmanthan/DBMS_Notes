🎯 CORE CONCEPTS TO EMPHASIZE
═══════════════════════════════════════════════════════

  1. FILE ORGANIZATION TYPES
     Heap: unordered → fast insert, slow search (full scan)
     Sorted/Sequential: ordered by key → fast range queries, slow insert
     Hashed: bucket by hash(key) → fast exact match, bad for ranges

  2. INDEX TYPES (the hierarchy students must know)
     Primary Index: on the ordering key of a sorted file, sparse
     Clustering Index: data rows physically sorted by index key
     Secondary Index: on a non-ordering column, always dense,
       does NOT reorder the underlying data

  3. B-TREE vs B+ TREE (the single most-tested distinction)
     B-Tree: data pointers in BOTH internal and leaf nodes
     B+ Tree: data pointers ONLY in leaf nodes, leaves linked as a list
     → B+ Tree wins for databases because:
       a) Internal nodes stay small → more fan-out → shorter tree
       b) Leaf linked-list makes RANGE queries fast (no re-traversal)

  4. HASHING
     Static Hashing: fixed number of buckets, degrades with growth
       (overflow chaining needed once buckets fill up)
     Dynamic Hashing: buckets grow/shrink with data (extendable hashing)

  5. INDEXES ARE A TRADE-OFF
     Faster reads (SELECT, WHERE, JOIN, ORDER BY)
     Slower writes (INSERT/UPDATE/DELETE must also update every index)
     → Index columns used in WHERE/JOIN often, not every column blindly

═══════════════════════════════════════════════════════
🔧 HANDS-ON: INDEX + EXPLAIN ON COLLEGE DB
═══════════════════════════════════════════════════════

  Before indexing:
    EXPLAIN SELECT * FROM student WHERE dept_id = 1;
    → type: ALL (full table scan), rows: all rows in table

  Create index:
    CREATE INDEX idx_student_dept ON student(dept_id);

  After indexing:
    EXPLAIN SELECT * FROM student WHERE dept_id = 1;
    → type: ref (index lookup), rows: only matching rows

  Ask students to compare the 'rows' column before/after —
  that's the concrete, visible proof an index worked.

═══════════════════════════════════════════════════════
📋 QUICK QUIZ ANSWERS
═══════════════════════════════════════════════════════

  Q1: Which file organization is best for exact-match lookups?
      → Hashed
  Q2: Which file organization is best for range queries (BETWEEN)?
      → Sorted / B+ Tree index
  Q3: Can a table have more than one clustering index?
      → No — only one, since data can only be sorted one way
  Q4: Where does a B+ Tree store data pointers?
      → Only in leaf nodes
  Q5: Why do leaf nodes in a B+ Tree link to each other?
      → To make range queries fast without re-traversing the tree

═══════════════════════════════════════════════════════
⚠️ COMMON STUDENT MISTAKES TO WATCH FOR
═══════════════════════════════════════════════════════

  1. Assuming more indexes always means better performance
  2. Confusing clustering index with primary key (related, not identical)
  3. Indexing every column "just in case"
  4. Forgetting indexes slow down INSERT/UPDATE/DELETE
  5. Thinking B-Tree and B+ Tree are interchangeable terms
  6. Not checking EXPLAIN output before assuming an index is being used

💡 TEACHING TIPS
═══════════════════════════════════════════════════════

  1. Use the "book index" analogy — flipping every page vs jumping
     to the index page for a topic
  2. Draw a B+ Tree on the board and physically trace a range query
     using the leaf-node linked list
  3. Run EXPLAIN live — the "rows" column dropping is the payoff moment
  4. Time an actual query before/after indexing on a larger sample
     table if possible — real numbers land better than theory alone
  5. Emphasize indexing is a DESIGN DECISION, not a free upgrade
