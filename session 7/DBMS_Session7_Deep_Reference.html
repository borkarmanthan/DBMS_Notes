1. File Organization — The Foundation

Before any index exists, rows must physically live somewhere on disk. The way they're arranged sets the baseline cost of finding them — indexes are built on top of this, not instead of it.
TypeHow It Stores RowsBest ForWeak Point
HeapUnordered, appended anywhere freeFast inserts — O(1)Full scan needed to find anything — O(n)
Sorted / SequentialPhysically ordered by a keyRange queries (BETWEEN, <, >) — binary search, O(log n)Insert requires shifting rows / reordering
HashedBucketed by hash(key)Exact-match lookups — O(1) averageTerrible for range queries — hashing destroys order

Worked Example

A university's admissions table is always queried by exact roll number, never by a range. Best organization? Hashed — O(1) equality lookups, and its weakness (bad range queries) never comes into play here.

Exam Question

"A log table is insert-heavy and almost never queried. Which file organization fits best, and why?" → Heap — fast inserts are what matters; search cost is irrelevant if searches rarely happen.

2. Why Indexes Exist — Index Types

The Book Index Analogy

Without an index: flip through every page looking for "Normalization" = Full Table Scan.
With an index: jump straight to "Normalization ... pg 142" = Index Lookup.
A database index is a separate, smaller structure that points directly at matching rows instead of scanning the whole table.

Three Index Types

TypeBuilt OnReorders Data?Density
Primary IndexThe ordering key of a sorted fileYes — file is sorted by itSparse
Clustering IndexA non-key ordering columnYes — only ONE per tableSparse
Secondary IndexAny other columnNoAlways dense

Worked Example

student(roll_no, name, dept_id, cgpa), physically stored sorted by roll_no.

  • Index on roll_no → Primary Index (it's the physical sort key)
  • If the table were instead sorted by dept_id → that index would be a Clustering Index
  • Index on cgpa → Secondary Index — matching rows are scattered everywhere on disk, so every single row needs its own entry (dense)
Trick question for class: "Can a table have a Primary Index AND a Clustering Index at the same time?" → No. They're the same concept — an index on the physical row order — just named differently depending on whether that sort key happens to be the actual primary key.

3. B-Tree — Structure & Worked Example

A balanced tree where every node — internal and leaf — stores both keys AND data pointers.
[ 30 | 60 ] / | \ [10|20] [40|50] [70|80]

Worked Insertion Example (order-3 B-Tree, max 2 keys/node)

Insert 10, then 20, then 30:

Insert 10 → [10] Insert 20 → [10, 20] Insert 30 → node overflows (3 keys > max 2) → splits, middle value (20) moves UP to become new root Result: [20] / \ [10] [30]
  • Every node keeps keys sorted
  • Search, insert, delete all run in O(log n)
  • Splits propagate upward automatically — this is how the tree stays balanced
The limitation: because internal nodes carry data pointers too, each node takes more space → fewer keys fit per disk page → taller tree → more disk reads. This is the entire motivation for the B+ Tree.

4. B+ Tree — Structure & Worked Example

Internal nodes hold only keys (pure routing). ALL data lives in leaf nodes, which are linked together like a chain.
[ 30 | 60 ] <- internal: keys only, no data / | \ [10|20]→[30|40|50]→[60|70|80] <- leaves: ALL data, linked list
B-TreeB+ Tree
Data pointersInternal + leaf nodesLeaf nodes ONLY
Internal node sizeLarger (keys + data)Smaller (keys only) → more fan-out
Range queriesMust re-traverse treeFast — just walk the leaf linked list

Worked Range Query Example

Query: SELECT * WHERE key BETWEEN 40 AND 70

B-Tree: must traverse from root and potentially revisit multiple subtrees, since matching data can live in internal nodes anywhere.

B+ Tree: ONE root-to-leaf descent to find 40, then just walk the leaf chain rightward: 40 → 50 → 60 → 70 → done. No further tree traversal needed.

Worked Fan-Out / Disk-Read Example

A B+ Tree with fan-out 100 holding 1,000,000 records needs approximately:

log₁₀₀(1,000,000) ≈ 3 levels

Fewer levels = fewer disk reads to reach a leaf. Since disk I/O — not comparisons — is the expensive operation, this is why MySQL InnoDB, PostgreSQL, and Oracle all default to B+ Trees for indexing.

5. Hashing — Static vs Dynamic

Static HashingDynamic Hashing
Fixed number of bucketsBuckets grow/shrink with data
hash(key) % num_bucketsExtendable hashing splits buckets on demand
Degrades as data grows — overflow chains formNo overflow chain degradation

Worked Example — Static Hashing

4 buckets, hash(key) = key % 4:

Insert 12 → bucket 0 Insert 25 → bucket 1 Insert 8 → bucket 0 (collision with 12 → overflow chain forms)

As more keys arrive, chains grow and lookup degrades toward O(n) — this is static hashing's core weakness. Dynamic hashing fixes this by splitting an overflowing bucket instead of chaining onto it.

Hashing is excellent for equality lookups (WHERE roll_no = 101) but useless for range queries (WHERE cgpa > 8.0) — the hash scrambles any natural ordering.

6. Hands-On: CREATE INDEX + EXPLAIN

Before Indexing

EXPLAIN SELECT * FROM student WHERE dept_id = 1; -- type: ALL (full table scan) -- rows: (every row in the table)

Create the Index

CREATE INDEX idx_student_dept ON student(dept_id);

After Indexing

EXPLAIN SELECT * FROM student WHERE dept_id = 1; -- type: ref (index lookup) -- rows: (only matching rows)
The rows column dropping is the concrete, visible proof the index is being used — pause here and let it sink in before moving on.

7. Full Exam Question Bank

  1. Compare heap, sorted, and hashed file organization — one advantage and one disadvantage each.
  2. Why can a table have only one clustering index but many secondary indexes?
  3. Draw and label the structural difference between a B-Tree and a B+ Tree.
  4. A B+ Tree leaf node points to another leaf node. What is this used for?
  5. Why do database systems prefer B+ Trees over B-Trees for indexing?
  6. Differentiate static and dynamic hashing.
  7. Given EXPLAIN output showing type: ALL, rows: 5000 before an index and type: ref, rows: 3 after — explain what changed internally.
  8. Give an example of a column you should NOT index, and justify it.
    Model answer: a low-cardinality boolean column like is_active, or a write-heavy column rarely used in WHERE/JOIN — index maintenance cost outweighs the read benefit.
  9. True/False with justification: "Adding more indexes always improves query performance."
    Model answer: False — every index adds write overhead (INSERT/UPDATE/DELETE must maintain it too); it's a trade-off, not a free upgrade.
  10. Numerical: A B+ Tree has fan-out 100 and holds 1,000,000 records. Approximately how many levels does it need? (≈3 — tests understanding of why fan-out matters, not just vocabulary.)
