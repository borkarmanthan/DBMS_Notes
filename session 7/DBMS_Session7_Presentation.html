🗂️ File Organization

Before indexes exist at all, rows have to be physically stored somewhere on disk. How they're stored determines how fast they can be found.

🌳 B-Tree Structure

A balanced tree where every node holds keys AND data pointers — including internal (non-leaf) nodes.
[ 30 | 60 ] / | \ [10|20] [40|50] [70|80]
  • Every node keeps keys sorted
  • Search, insert, and delete all run in O(log n)
  • Data pointers live in internal nodes too — this is the key difference from B+ Tree

🌲 B+ Tree — Why Databases Prefer It

[ 30 | 60 ] <- internal: keys only, no data / | \ [10|20]→[30|40|50]→[60|70|80] <- leaves: ALL data, linked list
B-TreeB+ Tree
Data pointersInternal + leaf nodesLeaf nodes ONLY
Internal node sizeLarger (keys + data)Smaller (keys only) → more fan-out
Range queriesMust re-traverse treeFast — just walk the leaf linked list
Smaller internal nodes fit more keys per disk page → shorter tree → fewer disk reads. This is why almost every production database index is a B+ Tree, not a plain B-Tree.

#️⃣ Hashing

Static Hashing

  • Fixed number of buckets
  • hash(key) % num_buckets
  • Degrades as data grows — overflow chains form

Dynamic Hashing

  • Buckets grow/shrink with data
  • Extendable hashing splits buckets on demand
  • No overflow chain degradation
Hashing is excellent for equality lookups (WHERE roll_no = 101) but useless for range queries (WHERE cgpa > 8.0) — the hash scrambles any natural ordering.

🔧 Hands-On: CREATE INDEX + EXPLAIN

Before Indexing

EXPLAIN SELECT * FROM student WHERE dept_id = 1; -- type: ALL rows: (every row in the table)

Create the Index

CREATE INDEX idx_student_dept ON student(dept_id);

After Indexing

EXPLAIN SELECT * FROM student WHERE dept_id = 1; -- type: ref rows: (only matching rows)
The rows column dropping is the concrete, visible proof the index is being used — this is the moment to pause and let it sink in.
