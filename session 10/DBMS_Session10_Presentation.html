💥 Why Recovery? Types of Failures

Failure TypeWhat Happens
Transaction FailureA logical error, e.g. a constraint violation — only that transaction is affected
System CrashPower/OS failure — everything in volatile memory is lost
Disk FailureNon-volatile storage itself is physically damaged
Backups protect against disk failure. Logs and checkpoints protect against crashes. They are NOT interchangeable safety nets.

📝 Write-Ahead Logging (WAL)

The core rule: the log record for a change MUST be written to stable storage BEFORE the actual data page is written to disk.

Log Record Format

<Transaction_id, Data_item, Old_value, New_value>
This single rule is what makes recovery possible at all — if the system crashes mid-write, the log already knows what was intended.

✅ Checkpoints

A periodic snapshot recording which transactions were active at that moment.
Log start ----[checkpoint]----[checkpoint]----CRASH ↑ Recovery only replays from HERE, not from log start

Without checkpoints, every recovery would have to replay the ENTIRE log history — checkpoints make recovery time bounded and predictable.

🔁 Deferred vs Immediate Update

Deferred UpdateImmediate Update
When DB is writtenOnly after commitCan happen before commit
REDO needed?YesYes
UNDO needed?No — nothing was written earlyYes — for uncommitted writes

ARIES — 3 Phases

Analysis → Redo → Undo

Analysis: find transactions active at crash. Redo: repeat history since last checkpoint. Undo: roll back the "loser" transactions.

💾 Backup Strategies

TypeWhat's Backed Up
FullThe entire database, every time
IncrementalOnly changes since the last backup (of any type)
DifferentialOnly changes since the last FULL backup

🔧 Hands-On: Backup, Restore & Binary Log

# Full backup mysqldump -u root -p college_demo > college_backup.sql # Simulate loss (on a throwaway copy!) DROP TABLE student; # Restore mysql -u root -p college_demo < college_backup.sql # Inspect MySQL's own write-ahead-style log SHOW BINARY LOGS; SHOW BINLOG EVENTS IN 'binlog.000001';
The binary log IS a real-world example of write-ahead logging — every change is logged, enabling replay-based recovery.
